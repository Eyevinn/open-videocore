# Vendored service contracts

Machine-readable contracts for the OSC services this API calls, copied here
**byte-identically** from their upstream source and pinned to a commit. They exist
because the OSC catalog publishes only a service's *provisioning* config
(`get-service-schema` → the fields needed to create an instance), never the runtime
request/response shape — so there is nothing else a contract test can be written
against. See the friction log in the agents repo,
`docs/osc-feedback/incoming-catalog-no-machine-readable-runtime-contract.md`.

A snapshot here is the input to a test, not documentation: the test diffs the
contract our code has recorded against the snapshot, so a refresh that changes
anything material fails CI and has to be dealt with deliberately.

### Not every artefact here can be byte-identical

`encore-findbystatus-paging.json` and `eyevinn-ffmpeg-s3-job-and-logs.json` are
**transcriptions**, not copies, and each says so in its own `$comment`.

For `eyevinn-ffmpeg-s3-job-and-logs.json` the reason is the same one that explains this
whole directory, in its purest form: the OSC catalog publishes only the service's
provisioning config, and the service publishes no OpenAPI document of its own at all —
it is a CLI in a container, so the "contract" for a job body is the argv parser in
`src/cli.ts` and the command rewriter in `src/ffmpeg.ts`. Refreshing it means re-reading
the symbols listed in `source.symbols` at a newer commit and re-checking the recorded
`blobSha256` values, not re-downloading a document. Note that several of its fields are
`null` with `requiresLiveRun: true`: they are unanswered, not answered-as-absent.

`encore-findbystatus-paging.json` is a transcription for a different reason, and says so
in its own `$comment`. Encore serves its OpenAPI document from a running instance
(`GET /v3/api-docs`, generated by springdoc) and publishes no static equivalent,
so there is no upstream file to `curl`. Worse, the one property the scaler's
drop detection depends on — what `page.totalElements` counts — is not stated by
that document at all; it is only decidable from the source
(`RedisService.findByQuery` returns `PageImpl(jobs, pageable, count)` with
`count` being the full match count). So the artefact records values read out of
upstream source at a pinned commit, each cited to `file:line`, plus a live
response capture for the things only a running service can answer (the silent
`size` clamp). Refreshing it means re-reading those lines at a newer commit, not
re-downloading a file.

## Refreshing a snapshot

```bash
curl -sS -o docs/contracts/eyevinn-function-scenes-api.json \
  https://raw.githubusercontent.com/Eyevinn/function-scenes/<sha>/api.json
npx vitest run test/scene-detect-contract.test.ts
```

Update the pinned commit in the table above **and** in
`FUNCTION_SCENES_CONTRACT_SOURCE` (`src/pipeline/function-scenes-contract.ts`) in
the same change. If the test now fails, the service has changed under us: fix the
recorded contract and the call together — do not relax the test.

Keep the file exactly as upstream serves it (no reformatting), so a refresh diff
shows only what the service actually changed.

For `encore-findbystatus-paging.json` there is no download step — re-read the
symbols listed in `source.symbols` at the new commit, update `source.ref` /
`source.refDate` / `source.verifiedOn` and `ENCORE_PAGING_CONTRACT_SOURCE`
(`src/encore-scaler/encore-paging-contract.ts`) together, then run
`npx vitest run test/encore-findbystatus-contract.test.ts`.
